## 技术咨询：Shadertoy Ndc3zl（云海之上 · 手绘风日落）能否用于本站

- 用户提出想把 `https://www.shadertoy.com/view/Ndc3zl` 的着色器效果应用进本项目。**本轮为纯咨询，未修改任何代码**（遵守 AGENTS.md §7）。
- 该 shader 内容：手绘风日出/日落 + 云层 + 桥剪影，暖色调。同类参考见 ghostty-shaders issue #67。
- 未能直接抓取源码：Shadertoy 页面为 JS 渲染，官方 API 需 key（返回 `{"Error":"Invalid key"}`）。后续若要落地，需用户自行从页面复制 GLSL，并确认 pass 数量（是否含 Buffer A/B）与是否依赖 iChannel 贴图、以及作者标注的授权协议。
- 给出的核心结论：
  1. 属于易移植类型（单个 Image pass + 全屏四边形 + uniform 桥接，约 80~120 行 TS，无需 three.js）。
  2. 与本站现有设计取向的冲突点：`app/components/layout/HeroBanner.vue` 明确以「0ms 首屏、零水合延迟」为目标，WebGL 无法 SSR，因此建议静态 webp 保底 + canvas 渐入叠层（渐进增强）。
  3. 双主题冲突：该 shader 为暖色日落，与暗色主题「星夜之畔」（靛蓝/紫）气质不符，需决定「仅亮色启用 / 双调色板 uniform / 换页面」。
  4. 性能需降级策略：DPR 上限、半分辨率渲染、IntersectionObserver 离屏暂停、document.hidden 暂停、prefers-reduced-motion 禁用。
- 建议的试水落点优先级：`app/error.vue`(404) → `app/pages/about.vue` → HeroBanner → 文章详情页背景。
- 待用户回答的关键问题：使用范围、暗色主题如何处理、移动端是否允许降级静态图、是否保留原作者署名（授权合规）。

## 第四轮：夜间风格改造（同日）

用户要求给动画加夜间风格。方案（已实现）：
- **`uNightBlend` uniform**（0=日落 / 1=深夜）：ShadertoyBackdrop preamble 增加声明，props.nightBlend（默认 0）在 setCommonUniforms 按位置注入（着色器未声明则自动跳过，向后兼容）。
- **HeroBanner**：`useColorMode()` 判定主题 → nightBlend ref 经 900ms rAF tween 平滑过渡 → `:night-blend` 传入；onMounted 按当前主题初始化，避免暗色用户首帧闪白。
- **image.frag 站点扩展**：夜间调色（降饱和 0.55 → 蓝移 vec3(0.45,0.58,0.92) → 压暗 0.52 → 补深夜环境光 vec3(0.015,0.03,0.07)）+ 月亮（右上 uv(0.76,0.78)，exp 光晕+圆盘）+ 星空（skyMask 用白天色 b-r>0.25 判定只落天空，3px 网格 hash 星点 0.35% 密度 + iTime 闪烁）；uNightBlend=0 时与原作逐像素一致；Buffer A 场景代码未改动。
- 验证：GLSL 解析 3 PASS、ESLint 0 错误、日间截图回归正常。**夜间截图未能完成**：无头 Chrome 在沙箱内反复崩溃（/dev/shm 仅 10MB；`--force-color-scheme=dark` 直接 SIGTRAP；localStorage 引导页 + --screenshot 重定向时机不可靠），改由用户在预览面板点主题切换按钮实时验证。
- 环境教训：沙箱 /tmp 与 Bash 调用间不共享、safe-delete shim 拦截 >50 文件的批量删除（chrome profile 目录清理被拦）、连续多轮 headless chrome 会耗尽 shm——同一会话避免反复起 chrome，或每轮后 pkill。
- 临时文件 public/night_preview.html、__night_preview.html 已清理；dev server 保持运行于 3100 供用户预览。

## 第五轮：流速与 Firefox 卡顿优化（同日）

用户反馈：场景变化过快、Firefox 打开卡顿。处理：
1. **放慢流速**：buffer-a.frag `iTime*4.0` → `iTime*1.2`（约 1/3 速度，云/火车/桥整体变缓，文件头注释已标注为站点适配）。
2. **自适应降档**：ShadertoyBackdrop 渲染循环加帧率监测（90 帧滑动窗口），平均帧率 <45fps 时渲染分辨率逐步下调 0.75→0.6→0.45→0.4（下限 40%），触发 resize() 重建 FBO，控制台输出降档日志。这是 Firefox 卡顿的主解法（该 shader 逐像素 8 层 fbm × 14 层云，Firefox GPU/编译器组合明显更吃力）。
3. **消除每帧 GC 抖动**：iChannelTime 的 Float32Array 与 iDate 的 Date 对象提升为复用的 scratch 变量（此前每帧每 pass 各分配一次）。
- 验证：GLSL 3 PASS、ESLint 0 错误、dev server HMR 热更新生效（3100）。
- 关闭项目时发现：TaskStop 杀掉了跟踪的 shell，但 nuxt dev 的子进程（vite worker）脱离后残留监听 3100，且从沙箱内 pkill/ss//proc 均无法触达（进程在宿主侧命名空间）。**沙箱内起的长驻服务若要彻底关闭，优先在单条命令内完成或依赖会话结束回收**。该残留 dev server 无害，随会话结束自动消失，不影响用户自己的 3000 端口。
- 遗留观察点：若 Firefox 降档到 40% 仍卡，下一手段是 fps 上限（如 30fps）或减云层层数（fbm detail 8→6）。
